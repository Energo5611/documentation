# Полное техническое задание — Купика / KUPIKA

**Версия 1.1 • 10 октября 2026.** Мобильная PWA для многих независимых семей. Язык интерфейса — русский. Это целевая спецификация, не отчёт о готовом коде.

Обязательные дополнения: PHONE_AND_FAMILIES.md, DESIGN_SYSTEM.md, FLOATING_EFFECT.md, ACCEPTANCE.md. Версия 1.1 заменяет ранний черновик с email-входом и одной семейной установкой. Последние требования владельца выше ранних постеров.

## 1. Идея

Один близкий человек составляет или надиктовывает список, другой идёт в магазин и видит крупные карточки. Любой взрослый может быть автором и покупателем. Список дополняется в процессе, все разрешённые участники видят, что уже куплено. Есть голосовые сообщения и тёплая кнопка «Люблю! Целую.».

Приложение доступно разным семьям. Каждая создаёт собственное закрытое пространство, приглашает близких по телефону и не видит чужие данные. Публичный сервис не означает публичные списки.

**Не интернет-магазин:** никаких цен, сумм, валютных полей, скидок, оплаты, продавцов, доставки и оформления заказа. Количество, масса, объём, жирность и заметки нужны. Произвольную заметку не превращать в финансовую операцию и не удалять из неё все цифры.

Вне версии 1: видеозвонки, публичный мессенджер, поиск незнакомых людей, геолокация, чеки, бюджеты, интеграция с кассами/маркетплейсами, автозаказ товаров и рекламная лента. Детали старых постеров не расширяют объём автоматически.

## 2. Что подтверждено и что предлагается

Подтверждено: мобильная веб-версия; много семей; номер +7; приглашение по номеру и принятие другой стороной; равноправные покупки взрослых; дети; ручной/голосовой ввод; отдельное аудио; уведомления; синхронные покупки; три темы; единый логотип; стекло и парение; послойные листочки/магазин; отсутствие цен; общий фон в цвет продукта; «Люблю! Целую.».

Предлагаемые начальные параметры: код подтверждения номера через согласованный сервис; детские пожелания с подтверждением взрослого; до 12 участников на семью и 200 активных позиций в списке как изменяемые эксплуатационные лимиты; 120 секунд/10 MiB на голосовое, 60 секунд на надиктовку; локальный серверный STT; 90 дней для аудиосообщений и до 24 часов для временной надиктовки. Эти параметры не выдавать за отдельные утверждённые пожелания владельца.

Перед публичным запуском согласовать сервер/домен, подтверждение номера и бюджет, ресурсы STT, финальные ассеты, сроки хранения и правила публичного обслуживания. До этого можно полноценно разрабатывать на изолированных тестовых данных, но не открывать незашищённый вход реальным семьям.

## 3. Вход и независимые семьи

Первый экран: +7 уже стоит, вводятся ещё 10 цифр. Маска +7 (___) ___-__-__. Поддержать вставку и безопасную нормализацию, в базе телефон как строка канонического вида, не integer. Никакой обязательной почты. Номер — идентификатор, не секретный пароль [S20]. Детали проверки, SMS-лимитов, восстановления и приглашений — PHONE_AND_FAMILIES.md.

После подтверждённого входа: имя, аватар, тема; затем существующее приглашение либо создание семьи. Не создавать автоматически вторую пустую семью человеку, который пришёл принять приглашение. Следующие открытия используют действующую защищённую сессию [S21].

Семья — не общий пароль. У каждого отдельный User с постоянным UUID и Membership. Семейные данные изолировать на сервере для HTTP, realtime, медиа, worker и кэша. Нельзя доверять familyId из клиента без проверки. Разные семьи не объединяются по номеру родственника, имени, Wi-Fi или устройству.

Владелец управляет пространством, взрослый имеет все права покупки, ребёнок — ограниченные. Право приглашений `canManageFamily` выдаётся взрослому отдельно. Пол и тема оформления не определяют права.

| Действие | Взрослый | Ребёнок по умолчанию |
|---|---|---|
| Видеть списки | Разрешённые семейные | Разрешённые взрослым |
| Добавлять товары | Сразу в общий список | Пожелание до подтверждения |
| Править общие позиции | Да | Только своё неподтверждённое пожелание |
| Отмечать покупки | Да | По разрешению на конкретный список |
| Голос/короткий текст | Внутри семьи | Внутри семьи по разрешению |
| Приглашать | При canManageFamily | Нет |
| Архивировать список | Да, явное действие | Нет |
| Менять тему | Да | Да, без повышения роли |

Последнего владельца нельзя удалить до передачи управления взрослому. Удалённый участник теряет новые запросы/события/медиа. Мгновенное стирание ранее скачанного с отключённого устройства не обещать.

Личный аккаунт ребёнка в версии 1 также имеет собственный номер. Профили без номера — возможное расширение после согласования, не основной сценарий. Не выводить возраст из номера; не требовать адрес, школу и фото.

## 4. Приглашение

«Семья → Пригласить» → +7 и 10 цифр → проверка введённого номера → предлагаемая роль → pending-запрос. На другой стороне «Принять» / «Отклонить». Только принятие проверенным получателем создаёт членство.

Зарегистрированный человек получает внутреннее уведомление и, при доступной подписке, push. Незарегистрированному можно передать ссылку; после подтверждения именно приглашённого номера он видит запрос. Автоматические SMS-приглашения не включать без согласия и бюджета. До принятия не раскрывать покупки, детей, аудио и телефоны семьи.

Приглашение имеет срок, отзыв, защиту от повторов и лимиты. Ссылка сама по себе не даёт доступа, её нельзя принять другим номером. Получатель может отклонить и блокировать нежелательные повторения. Нет публичного справочника пользователей по телефонам. Полный контракт — профильное дополнение.

## 5. Списки и походы

Список: `draft` — личный автора; `active` — общий; `archived` — история. После публикации нельзя молча сделать общий список приватным. В одной семье может быть несколько списков: «Домой», «К выходным» и пользовательские названия.

Поход — отдельная сущность ShoppingTrip: `shopping`, `finished`, `cancelled`. «Я в магазин» сообщает намерение, не включает геолокацию и не блокирует список для второго покупателя. Два взрослых могут покупать одновременно. «Я дома» завершает поход, не список.

В списке: название, автор, участники, кто в магазине, число «Куплено 3 из 8», фильтры «Нужно», «Куплено», «Все», категории. Пожелания ребёнка pending не входят в число необходимых до одобрения.

«Люблю! Целую.» в черновике атомарно публикует список и тёплое сообщение. В активном — отправляет сообщение/обновление без создания второго списка. Не закрывает, не архивирует, не запрещает добавления. Повторный тап не дублирует. Перед отправкой виден адресат «Семье» либо конкретный участник; это адресат уведомления, не изменение приватности общего списка.

Офлайн публикация ставится в очередь с текстом «Отправим, когда появится связь». «Отправлено» только после сервера. В активном списке новые товары общие после серверного принятия, не требуют отдельного тёплого сообщения на каждый продукт. Серии добавлений объединяются.

Когда всё куплено — спокойное подтверждение, список остаётся доступен. Архивирование отдельно и с предупреждением при незакупленных позициях. Копия из истории создаёт новые ID, статус needed и не меняет оригинал.

## 6. Сквозной сценарий

A создаёт черновик → вводит/надиктовывает молоко, хлеб, сыр → проверяет → «Люблю! Целую.» → B получает список → «Я в магазин» → B нажимает хлеб → статус purchased, общий фон становится песочным → A видит покупку → A добавляет кофе → B видит новую карточку и уведомление → B отправляет голос «Такого сыра нет, взять другой?» → A отвечает → B завершает поход «Я дома».

На следующий день A и B меняются ролями без перенастройки. С другого аккаунта семьи D этот список не открывается по ID, ссылке, файлу, realtime-подписке или номеру A.

## 7. Карточки продуктов

Большие карточки с объёмным узнаваемым изображением, названием, количеством/единицей и заметкой. Две колонки по умолчанию; одна при узком экране/увеличенном тексте. Никаких цен. Статус и действие понятны без цвета.

Данные: productId nullable, name, quantity decimal nullable, unit, note, category, assetId, ambientColor, authorId, purchasedBy/At, version. Жирность 3,2% — характеристика, а не количество; «2 пакета молока» — две упаковки. Неизвестное количество явно отмечено, а не выдумано.

Статусы покупки `needed`, `purchased`, `unavailable`. Отдельное согласование `pending`, `approved`, `rejected`. Отдельный локальный sync-state `pending`, `synced`, `failed`, `conflict`. Не смешивать факт покупки с доставкой изменения серверу.

Тап большой зоны карточки в режиме покупки — явная смена нужное/купленное. Кнопка меню/изменение количества/проигрывание голоса не запускают этот тап. Не использовать long press как единственный способ редактирования. Семантически не вкладывать кнопки друг в друга.

Купленный товар не исчезает мгновенно из-под пальца. Галочка, подпись, автор, мягкое изменение; перегруппировка после взаимодействия с сохранением прокрутки. Повторный тап и меню позволяют отменить.

Изменение товара/количества после покупки предлагает вернуть его в needed, а не оставляет новую просьбу незаметно выполненной. Частичные покупки — расширение после версии 1. Дубликаты объединять только с подтверждением и при совместимых единицах/характеристиках. Разное молоко и несовместимые единицы не суммировать молча.

«Нет в магазине» — отдельное действие. Можно задать вопрос голосом/текстом с привязкой к товару. Замена не назначается автоматически; сохраняет связь с исходной просьбой и объяснение.

## 8. Ввод и иллюстрации

Ручной ввод одной позиции, многострочного списка, поиск в словаре/синонимах. Массовый ввод и надиктовка всегда дают редактируемый предпросмотр. Запятые в десятичных числах не разбивают товар ошибочно. Библиотека — словарь изображений, не каталог цен/наличия магазина.

До визуальной приёмки минимум 24 качественных ассета: молоко, хлеб, сыр, яйца, масло, творог, йогурт, сметана, яблоки, бананы, помидоры, огурцы, картофель, морковь, зелень, лимон, курица, рыба, рис, макароны, чай, кофе, вода, бытовой товар. Для остальных — нейтральная иллюстрация категории. JSON содержит примеры, а не готовые изображения.

Изображения объёмные, натуральные материалы, мягкие тени, без глаз/лиц. Генерируются/готовятся один раз, не за платный запрос при каждом добавлении. Не брать случайные фото магазина или чужую фирменную упаковку без основания. Пользовательское фото: проверка формата/размера, удаление EXIF, приватное хранение.

## 9. Надиктовка списка

Отдельное действие «Надиктовать список»: запрос микрофона по нажатию → таймер → остановка → распознавание → разбор на позиции → редактируемый предпросмотр → подтверждение. Речь «молоко два пакета, хлеб один, сыр двести граммов, яйца десять штук» даёт четыре кандидата, не отправляет исходное аудио семье.

Сохранять исходный текст, массив name/quantity/unit/note, неоднозначности needsReview. Не выдумывать confidence при отсутствии его в движке. Неизвестные слова сохранять для исправления; тишина не должна создавать товары. Фразы о предпочтении «как в прошлый раз» оставлять заметкой, не придумывать бренд.

Основной совместимый путь: MediaRecorder → приватная загрузка → серверный SpeechToTextProvider → parser. Browser SpeechRecognition не единственный обязательный механизм из-за различий поддержки/реализации [S04]. Кандидат локального STT — faster-whisper с русским языком; CPU/int8 и размер модели выбирать после реального замера [S11]. Облачный платный API не подключать без согласования. Базовый словарь/парсер не требует LLM.

Задание распознавания асинхронное, имеет статус/ошибку/повтор и лимит очереди. Не исполнять надиктованное как команды серверу. Временное аудио удаляется по сроку; сам опубликованный текст остаётся частью списка. Отказ STT не блокирует ручной ввод.

## 10. Отдельные голосовые сообщения

Действие «Голосовое» записывает звук для близких, НЕ превращает его автоматически в товары. Запись до 120 секунд/10 MiB как начальные лимиты, таймер, стоп, отмена, прослушать, отправить. Сообщение связано со списком и при необходимости товаром. Также короткий текст до 1000 символов и реакция-сердце; полноценный публичный мессенджер не нужен.

Получатель: автор, реальная аудиозапись, play/pause, длительность, позиция, дата. Один проигрыватель одновременно, без автозапуска. «Сохранено сервером» не значит «человек прослушал». Статус прослушивания можно показывать только при реальном событии воспроизведения по документированному правилу.

Микрофон требует защищённого контекста и разрешения [S03]. Формат проверять через MediaRecorder.isTypeSupported, не фиксировать WebM для всех устройств [S05]. Сервер при необходимости приводит аудио к совместимым форматам. Проверять iPhone→Android и обратно.

Закрытие/отмена освобождает треки микрофона. Прерывание звонком/блокировкой обрабатывать как прерванную запись, не обещать запись в фоне. Офлайн запись может остаться локальным черновиком; отправка после связи с явным pending. Повтор upload/finalize не создаёт дубликатов. Ошибки записи/доступа/размера/обработки имеют понятные действия.

## 11. Детские пожелания

Взрослый приглашает ребёнка по его номеру с ролью child, ребёнок принимает. По предлагаемому умолчанию добавление — пожелание, требующее подтверждения. У ребёнка «Ждёт подтверждения», у родителя «Саша просит йогурт». Одобрение публикует товар; отклонение мягкое, без наказаний и рейтингов.

Право отмечать покупки взрослый может выдать на выбранный список. Самостоятельная смена темы/имени/client role не повышает права. Детский профиль не управляет взрослыми, приглашениями, архивами и настройками безопасности. Чужих контактов и публичных сообщений нет.

## 12. Навигация и экраны

Нижняя навигация взрослого: «Список», «Сообщения», «Семья», «Профиль». Добавление доступно большим пальцем. У ребёнка убрать недоступные настройки, но сервер всё равно проверяет запреты.

Экраны: знакомство; ввод +7; подтверждение номера; имя/аватар/тема; создание/принятие семьи; входящие приглашения; активные списки; главный список; добавление/надиктовка с предпросмотром; детали товара; голос/короткие сообщения; уведомления; семья/разрешения; профиль/устройства/номер; история; помощь установки PWA.

У главного списка: логотип, название, аватары, кто в магазине, прогресс, фильтры, карточки, добавить/голос. Нельзя загромождать рабочую область рекламными баннерами и слоганами. На desktop использовать пространство для списков слева и сообщений справа, мобильный сценарий основной.

Обязательные состояния: пусто, все куплено, загрузка, ошибка, офлайн, pending, конфликт, доступ отозван, приглашение истекло/отклонено, неверный/истёкший код входа, лимит кода, микрофон запрещён, STT недоступен, push запрещён/не поддержан. Не оставлять бесконечный спиннер.

## 13. Бренд, темы и объём

Единый логотип — французская небольшая лавка с полосатой маркизой и тремя листочками. Последний запрос: каждый лист и магазин на разной глубине, магазин спереди, индивидуальные мягкие тени и ощущение воздуха. Нужны отдельные слои/мастер-ассеты, не плоский постер. Полные правила — DESIGN_SYSTEM.md и FLOATING_EFFECT.md.

Три темы: мужская «Север» — сливочно-серая база, сине-серые акценты; женская «Пудра» — сливочный/пудрово-бежевый, без яркого розового; детская «Солнечная» — сливочно-жёлтый/абрикос/мята, не копия мужской. Тема персональная, не право доступа. Логотип не перекрашивать.

Карточки матово-стеклянные, мягкий край, деликатная тень и парение. Без постоянного покачивания. Параллакс логотипа допускается только очень лёгкий внутри приложения; системная иконка PWA — статический экспорт, управление её внешней анимацией системой не обещать [S18].

UI-текст настоящий HTML, не картинка с постера. Предлагаемые шрифты Inter/Nunito проверить на кириллицу и лицензию [S14, S15]; художественный логотип не пересобирать случайным шрифтом.

## 14. Общий фон в цвет купленного продукта

Обязательная отличительная функция. При локальном тапе, который отмечает покупку, общий фон всего экрана под шапкой/карточками/нижней навигацией мягко приобретает оттенок продукта. Реагирует сразу оптимистично. Подсветки только карточки недостаточно. Подтверждение сервера не повторяет анимацию.

Цвет заранее хранится в ambientColor. Молоко — сливочный, хлеб — песочный, сыр — приглушённый золотой, зелень — шалфей, кофе — какао, яблоко — соответствующий изображению зелёный/коралловый. Для пользовательской картинки цвет извлечь заранее с игнорированием белой подложки/прозрачности/глубоких теней; fallback — цвет категории. На каждом тапе не запускать тяжёлую обработку.

Переход ориентировочно 600 мс, диапазон 450–700 мс. Начальная смесь 76% базы темы + 24% продукта. Широкие мягкие градиенты, максимум два фоновых слоя с crossfade или эквивалент без накопления. Последний быстрый тап побеждает, переход из текущего видимого цвета без белой вспышки. В покое движения нет.

Фон сохраняется до следующей покупки/отмены/выхода/конца похода. Отмена последней покупки возвращает предыдущий действующий цвет текущего локального сеанса, иначе базу. Отмена старой карточки не сбрасывает более новый цвет. Серверный отказ откатывает покупку и фон. Удаление последней активной позиции пересчитывает состояние.

История фоновых действий локальная, не глобальный статус семьи. По умолчанию удалённая покупка синхронизирует карточку, но не перекрашивает экран составителя. Логотип, изображения, цвет текста и смысл ошибок/успеха не меняются. Настройки «Динамический фон» и «Уменьшить движение» обязательны [S08]. Проверить контраст на всех сочетаниях [S07].

## 15. Уведомления

Разделить realtime-данные, внутренние события и системный Web Push. Push — сигнал, не база данных и не доказательство прочтения.

Уведомлять о публикации, новых товарах/группе, голосе, походе, отсутствии товара, детском пожелании и приглашении. Каждую галочку синхронизировать, но по умолчанию не отправлять о каждой внешний push. Объединять краткую серию добавлений, например за 3 секунды. Автор не получает собственный push.

Внутренние события сохраняются с eventId/readAt, не теряются при исчезновении плашки. Push открывает актуальный список; старое уведомление не откатывает статус товара. Для неустановленного приложения без подписки push не существует — показывать честный статус запроса и способ поделиться приглашением.

На iPhone Web Push предусмотрен для Home Screen web apps начиная с iOS 16.4, разрешение после явного действия пользователя [S01]. Проверять функции, объяснять установку. Не гарантировать точное время доставки: влияют сеть, разрешения, режимы ОС.

Несколько устройств на пользователя. Хранить подписки по устройству, удалять невалидные 404/410, ретраи с backoff/дедупликацией. VAPID private key только на сервере. Тихие часы персональные. По умолчанию системный preview нейтральный, без телефона и содержимого детских голосов. Собственный звук системного push не обещать; звук внутри приложения только при допустимом взаимодействии.

## 16. Офлайн

После первого открытия кэшируются оболочка и ассеты; разрешённые актуальные списки и исходящая очередь — IndexedDB с разделением по userId/familyId. localStorage только для малых визуальных настроек, не общая семейная БД.

Офлайн видны ранее загруженные данные, можно добавить/править/отметить с явным pending. Чужие новые товары без связи не появляются. При онлайн/фокусе/открытии — реальная проверка сервера и синхронизация. Background Sync лишь дополнительная возможность из-за ограниченной поддержки [S06].

Сохранять зависимости: создание/публикация списка → товары → сообщения. Подтверждённое не дублируется при повторах. Очередь привязана к исходному отправителю и семье; её нельзя переотправить под чужой сессией. Выход предупреждает о неотправленном и очищает данные. Private API не класть в общий service worker cache. Новый service worker не перезагружает страницу, теряя очередь.

## 17. Архитектура

При отсутствии существующего кода рекомендуемый стек: React/TypeScript strict/Vite для клиента [S12]; Node поддерживаемой LTS/Fastify для API [S13]; PostgreSQL; HTTP-команды и Socket.IO realtime; worker задач; отдельный Python STT; приватное файловое хранилище. Это предложение, не причина переписать уже подходящий существующий проект.

Для первой нагрузки достаточно модульного монолита API и worker, без микросервисов/Redis по умолчанию. Очередь jobs в PostgreSQL с арендой/ретраями. STT тяжёлая задача, не блокирует запросы API. Для многих семей нужны квоты/справедливость очереди: одна семья не вытесняет остальных. Нагрузочные пределы измерить, не писать «неограниченное число семей» без проверки.

Frontend/API/realtime желательно за одним HTTPS-origin, постоянный процесс для realtime, reverse proxy, persistent volumes. Не выбирать serverless-среду, несовместимую с постоянными соединениями, без адаптации. Домен и расходы только после согласия. Версии библиотек проверить/закрепить lockfile; не `latest` в воспроизводимой production-инструкции.

Структура: apps/web, apps/api, workers/speech, packages/contracts, packages/design, db/migrations, tests, docs, assets/brand, assets/products. Допустимо упростить с сохранением границ.

## 19. Синхронизация и конфликты

Команда содержит operationId UUID, объект, expectedVersion и желаемое состояние. Покупка на сервере — `setStatus: purchased`, не неидемпотентный toggle. Actor определяется сессией. Проверить членство/право/семью перед изменением и доставкой.

Транзакция: проверить дедупликацию → заблокировать нужные строки → проверить версию → изменить → записать ListEvent и outbox → сохранить результат команды → commit. Счётчик sequence увеличивать транзакционно под блокировкой строки списка; не путать порядок auto-increment с порядком commit [S16].

Повтор той же operationId/тела возвращает прежний результат. Другое тело с тем же ID — конфликт. Две одинаковые покупки одного товара сходятся к одному состоянию без двух уведомлений. Несовместимые изменения одной версии — 409 с актуальным объектом, не молчаливое уничтожение правки. Разные товары можно менять независимо; не заменять весь список старым клиентским массивом.

Socket.IO сам не заменяет долговечный журнал событий [S09]. При reconnect получить пропущенные события по sequence либо снимок при устаревшем cursor, затем подтвердить/отправить локальную очередь. Пропуск и дубликат обнаруживаются; собственный ack не запускает UI-анимацию повторно. Доступ проверяется при подключении и подписке на каждый список; отозванные соединения закрываются.

## 21. PWA и доступность

Manifest: id, name/short_name «Купика», start_url, scope, standalone, обычная/maskable иконки, apple-touch-icon. Иконка одна для всех тем; не обещать её автосмену по аккаунту [S18]. Установка на iPhone объясняется через системное меню [S01]. Service worker обновляет версионированные ассеты и не теряет pending-данные.

Проверить актуальные на выпуске iOS Safari/PWA, Android Chrome/PWA, desktop Safari/Chrome/Firefox. Минимальную iOS 16.4 заявлять только в пределах реально проверенных функций; порог наличия push не равен гарантии всей совместимости. Feature detection, не один user-agent.

Контраст текста 4,5:1/крупного 3:1 [S07]. Проектный минимум нажатия 44×44 CSS px, основные детские действия 48–56 px, это не утверждение о нормативном минимуме AA [S17]. 200% текст, focus, клавиатура, screen reader, закрытие панелей, aria-live без чрезмерного шума. Учитывать safe-area и экранную клавиатуру.

Reduced motion и уменьшение прозрачности. Blur имеет непрозрачный fallback. Реалистичный 3D-вид может быть готовым рендером, WebGL на каждой карточке не нужен. Оптимизировать изображения, lazy-load, размеры, отсутствие layout shift. Не использовать целый бренд-постер как фон приложения.

Цели на заданном среднем устройстве/нормальной сети: локальный отклик покупки до 100 мс, p95 изменения второго открытого клиента до 2 секунд, отсутствие зависаний при быстрых тапах; стремиться к 60 fps. Это тестовые цели, не гарантии любой сети, и не сроки push.

## 22. Безопасность и публичный сервис

Проверки IDOR/ролей/межсемейного доступа, CSRF для cookies, Origin realtime, ограниченный CORS, безопасный вывод текста, CSP, лимиты файлов/запросов. UUID сам по себе не авторизация. Номер не секрет. До production согласовать верификацию и восстановление [S20–S22].

Приватное аудио выдавать после проверки доступа через endpoint/короткоживущую подписанную ссылку. Нет открытого /uploads с постоянными URL голосов. Проверять MIME и фактическое содержимое, удалять метаданные фото; не скачивать сервером произвольный URL пользователя без SSRF-защиты.

Не писать телефоны, коды, аудио, содержимое списков и детские данные в логи/аналитику/Git. Для диагностики requestId, тип ошибки, длительность и безопасные технические метрики. Не заявлять E2EE: HTTPS не равен сквозному шифрованию.

Для публичного сервиса обязательны помощь/обратная связь, блокировка нежелательных приглашений, лимиты SMS/STT, квоты хранения, удаление аккаунта/семьи, политика данных и проверка требований к детским пользователям для реального рынка. Это контроль перед запуском, не юридическое заключение. Служебный доступ к частным данным минимален и аудируется.

Резервные копии и сроки удаления описаны: мгновенное удаление из всех backups не обещать. При выходе и отзыве очищать текущие сессии/кэш. При удалении семьи запретить новые операции и поставить медиа на удаление.

## 23. Развёртывание

Воспроизводимый Docker/Compose либо аналог: API, worker, PostgreSQL, STT, закрытое хранилище, HTTPS reverse proxy. Отдельные dev/test/prod. Секреты только environment/secret store, .env не коммитить. В .env.example только имена и безопасные пустые значения.

Предлагаемые backup каждый день/30 дней хранения согласовать с возможностями сервера. Public release не запускать с mock SMS или тестовой обходной авторизацией.

## 25. Definition of Done

Все обязательные сценарии ACCEPTANCE.md пройдены с доказательствами. Две независимые семьи действительно изолированы. Вход и приглашение проверены, неизвестный номер не даёт чужой доступ. Голос не имитация. Общий фон и послойный логотип работают внутри приложения. Три темы и отсутствие цен соблюдены. Код воспроизводимо запускается, ошибки/офлайн/отзыв доступа обработаны, ограничения платформ описаны.

Непроверенный телефон/сервер/провайдер отметить NOT RUN; не называть тест успешным. PNG-постер и экранная анимация не заменяют backend. Запуск без обязательной функции возможен только как явно согласованная промежуточная версия.
