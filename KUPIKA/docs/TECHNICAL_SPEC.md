# Полное техническое задание: Купика / KUPIKA

**Версия:** 1.0. **Дата:** 10.10.2026. **Платформа:** мобильное веб-приложение с установкой как PWA. **Язык интерфейса:** русский. **Адресат:** Codex и разработчик, выполняющий внедрение.

Документ задаёт целевой результат; это не отчёт о готовой реализации. Технические ограничения сверены с первичными источниками, перечисленными в SOURCES.md. Числовые параметры дизайна, лимиты и архитектура ниже — проектные решения, а не характеристики уже работающего продукта.

## 1. Идея и границы продукта

Купика помогает близким договориться о покупках. Один человек записывает или надиктовывает, что нужно; другой видит крупные карточки в магазине. Любой взрослый может быть составителем и покупателем. Список дополняется во время похода, изменения и отметки видны участникам семьи.

Главное отличие от переписки — не поиск просьб среди сообщений, а актуальные карточки: что нужно, в каком количестве, что уже куплено, чего не было. Общение остаётся тёплым: вместо оформления заказа — «Люблю! Целую.».

**Нельзя превращать приложение в интернет-магазин.** В версии 1 нет цен, сумм, валютных полей, скидок, платежей, доставки, остатков магазинов, продавцов, ссылок на оплату и маркетплейсной корзины. Количество, масса, объём и характеристики вроде «3,2%» нужны. Свободная пользовательская заметка остаётся текстом и не анализируется как финансовая операция.

Также вне версии 1: звонки, видеосвязь, публичные чаты, поиск незнакомых людей, геолокация семьи, банковские интеграции, сканирование чеков, автоматический заказ товаров и рекомендательная лента. Рецепты, штрихкоды, бюджеты и бонусы, случайно попавшие в старые постеры, не входят в согласованный объём.

## 2. Подтверждённые требования и предлагаемые настройки

Подтверждено владельцем: семейная двусторонняя работа; дети; три оформления; единый логотип; крупные 3D-карточки; ручной ввод; надиктовка; отдельные голосовые сообщения; уведомления; синхронные покупки; кнопка «Люблю! Целую.»; отсутствие цен; стекло и парение; фоновый перелив в цвет купленного продукта.

Предлагаемые настройки версии 1, которые можно принять для начала реализации:

| Вопрос | Рабочее решение |
|---|---|
| Написание | Название в тексте и под иконкой «Купика»; латиница KUPIKA; художественная надпись с сердцем допускается только внутри утверждённого логотипа |
| Вход взрослых | Email и пароль, подтверждение адреса и восстановление; SMS не требуется |
| Подключение детей | Создаёт взрослый; одноразовое подключение устройства без обязательного email/телефона ребёнка |
| Детские товары | По умолчанию пожелания, подтверждаемые взрослым; права покупателя можно выдать на выбранный список |
| Темы | Пользователь выбирает оформление сам; роли и пол не определяются по имени или фотографии |
| Активность | Один семейный контекст в первой версии, несколько списков внутри семьи |
| Голос | До 120 секунд и 10 MiB на сообщение; до 60 секунд на одну надиктовку |
| Список | До 200 активных позиций; мягкие предупреждения, серверные ограничения |
| Семья | До 12 участников как настраиваемый эксплуатационный предел, а не особенность бренда |
| Распознавание | Серверный адаптер, базово локальный faster-whisper; внешний платный провайдер только после согласия |
| Хранение | Черновик распознавания удаляется максимум через 24 часа; отправленное аудио по умолчанию 90 дней; сроки настраиваемы |

До публичного запуска согласовать домен, сервер, почту для авторизации, ресурсы распознавания, финальные SVG/PNG логотипа и сроки хранения. Эти вопросы не мешают начать прототип. Не запрашивать заново уже подтверждённую концепцию.

## 3. Семья, роли и права

**Семья — общее пространство, а не общий пароль.** У каждого участника отдельная идентичность и настройки. Каждая запись, аудио, приглашение и realtime-событие привязаны к семье. Переключение аватара на чужой профиль не даёт доступа к чужой сессии.

Роли: `owner` — владелец семейного пространства; `adult` — взрослый; `child` — ребёнок. Управление семьёй задаётся отдельным разрешением `canManageFamily`. Создатель получает его; второму взрослому можно выдать при приглашении. Покупки у всех взрослых одинаковы независимо от этого разрешения.

| Действие | Владелец/взрослый | Ребёнок по умолчанию |
|---|---|---|
| Просмотр общих списков | Да | Только разрешённые семейные списки |
| Создание и публикация списка | Да | Нет; создаёт пожелания |
| Добавление товара | Сразу в общий список | Пожелание с ожиданием подтверждения |
| Изменение общего товара | Да | Только своё неподтверждённое пожелание |
| Отметить покупку | Да | При разрешении на конкретный список |
| Голосовое и короткий текст | Внутри семьи | Внутри семьи, при разрешении взрослого |
| Приглашения и управление детьми | При canManageFamily | Нет |
| Архивирование/удаление общего списка | Да, с подтверждением | Нет |
| Смена темы | Да | Да, без изменения полномочий |
| Смена взрослой роли/владельца | По защищённому действию владельца | Нет |

Нельзя удалить последнего владельца без передачи управления взрослому. Удалённый участник теряет доступ к API, realtime и файлам; активные соединения закрываются. Уже сохранённые на офлайн-устройстве данные невозможно гарантированно стереть мгновенно: очистка должна выполняться при следующем соединении/выходе, это ограничение честно документировать.

Ребёнок не видит настройки безопасности взрослых, приватные черновики и посторонние семьи. ФИО, дата рождения, школа, адрес, геолокация и фото ребёнка не обязательны. Достаточно имени/псевдонима и безопасного готового аватара.

## 4. Регистрация, приглашения, устройства

Первый взрослый регистрируется, создаёт семью, выбирает имя и тему. Второй получает ссылку/QR, входит в свою учётную запись и принимает приглашение. Не создавать аккаунт за другого взрослого без его действия.

Приглашение: случайный криптографический токен не менее 128 бит, в базе хранится хеш; ограниченный срок; одно использование; возможность отзыва; ограничение попыток. Открытие URL методом GET не должно само менять состав семьи — принятие отдельным подтверждённым POST. Для взрослого рабочий TTL 24 часа, для подключения устройства ребёнка 10 минут. Не писать токены в логи и внешнюю аналитику.

Родитель создаёт детский профиль и разрешения. На устройстве ребёнка подтверждает одноразовое подключение; сервер выдаёт сессию именно ребёнка. Смена на взрослого требует взрослой авторизации. Родитель видит устройства ребёнка и может отозвать их.

Пароли хранить только как устойчивые хеши Argon2id; параметры подобрать не слабее актуальных рекомендаций OWASP и проверить на сервере [S10]. Сессии — защищённые cookies HttpOnly/Secure/SameSite с ротацией и отзывом. Клиентские долгоживущие bearer-токены в localStorage не использовать. Восстановление доступа — одноразовое, ограниченное по времени и попыткам. PIN возможен позднее как дополнительная локальная блокировка, но не как единственная защита публичного сервера.

## 5. Сквозные сценарии

### 5.1. Список составляет один, покупает другой

Взрослый создаёт личный черновик, вводит или надиктовывает позиции, проверяет результат. Нажимает «Люблю! Целую.». Сервер переводит список в общий активный, создаёт одно уведомление с кратким содержимым и тёплое событие. Второй взрослый открывает его и нажимает «Я в магазин». Любой из участников может поменяться ролями без перенастройки.

### 5.2. Покупка по пути

Участник нажимает «Я в магазин» у существующего общего списка. Остальные видят его статус и могут дополнить список. Это ручной статус, не геолокация и не эксклюзивное назначение исполнителя.

### 5.3. Дополнение в магазине

Другой участник добавляет йогурт в активный список. После подтверждения сервером у покупателя появляется карточка с отметкой «Новое» и уведомление; текущая прокрутка и нажатие не прерываются. При закрытом приложении сервер пытается отправить Web Push. При отсутствии связи изменение остаётся в очереди отправителя и не выдаётся за доставленное.

### 5.4. Отметка и отмена

Тап по карточке в режиме покупки сразу показывает «Куплено», запускает плавный фон в оттенок продукта и отправляет идемпотентную операцию. Остальные получают серверное изменение. Повторный тап возвращает «Нужно купить». При ошибке сервера оптимистичная отметка откатывается, появляется понятное сообщение и действие повтора.

### 5.5. Нет товара и замена

Из меню карточки — «Нет в магазине». Участники видят отдельный статус, а не галочку покупки. Можно отправить голосовое или короткий вопрос. Взрослый предлагает замену с привязкой к исходному товару; подтверждённая замена сохраняет объяснение в истории. Автоматически подменять бренд, количество или продукт нельзя.

### 5.6. Пожелание ребёнка

Ребёнок выбирает/надиктовывает товар и отправляет пожелание. У родителя карточка «Саша просит йогурт», у ребёнка — «Ждёт подтверждения». Родитель добавляет в список или отклоняет мягкой фразой. Отказ не оформляется как наказание, не снижает баллы и не создаёт давления.

### 5.7. Завершение похода

Кнопка «Я дома» завершает только поход. Незакупленные позиции остаются. Когда куплено всё, показать спокойное «Всё куплено» и при желании отправить тёплое сообщение. Ничего не архивировать автоматически. Архивирование — отдельное явное действие взрослого с предупреждением о новых/некупленных позициях.

## 6. Списки и состояния

Состояния списка: `draft` — виден автору; `active` — общий; `archived` — доступен в истории, изменения запрещены до восстановления. Опубликованный список нельзя молча вернуть в приватный черновик.

Поход — отдельная сущность `ShoppingTrip` со статусами `shopping`, `finished`, `cancelled`. Допускаются два взрослых одновременно в магазине. На одного участника — не более одного активного похода для одного списка. Нельзя блокировать список только потому, что кто-то уже нажал «Я в магазин».

В активном списке добавления сразу общие; массовый ввод публикуется одним пакетом после предпросмотра. Не требовать повторного нажатия «Люблю! Целую.» для каждого нового продукта. Уведомления о короткой серии добавлений объединять.

Есть название, автор, участники, время изменения, счётчик «Куплено 3 из 8», фильтры «Нужно», «Куплено», «Все» и категории. Не считать пожелания, ожидающие подтверждения, купленными или необходимыми товарами.

Архив можно просматривать и копировать в новый список: новые позиции имеют новые ID и статус «Нужно купить», исходная история не изменяется. Общие семейные шаблоны и избранные продукты допустимы, но не приоритетнее основного сценария.

## 7. Товар и крупная карточка

Обязательные данные: название, количество/единица либо явное «Количество не указано», категория, заметка при наличии, изображение/заглушка, статус, автор добавления. Для купленного — кто и когда отметил. Для нового — маркер непросмотренного изменения.

Состояния покупки: `needed`, `purchased`, `unavailable`. Отдельное поле согласования `approvalStatus`: `pending`, `approved`, `rejected`. Покупка допустима только для approved. Отдельно локальное состояние синхронизации: `synced`, `pending`, `failed`, `conflict`; оно не заменяет статус товара.

Количество хранится как decimal, например строка `"0.5"`, а не денежный тип. Единицы: шт., уп., бутылка, г, кг, мл, л, пучок, набор, другая. Жирность и размер упаковки — характеристики, не количество. «Молоко 3,2%, 2 пакета» = две упаковки молока с заметкой о жирности.

На мобильном по умолчанию две колонки крупных карточек; вариант одной колонки для увеличенного текста. На 320 CSS px допустим переход в одну колонку. Основной режим списка сразу пригоден для покупок: тап по большой зоне отмечает товар. Отдельная доступная кнопка «Подробнее/Изменить» открывает нижнюю панель; её нажатие не должно случайно менять покупку. Нельзя делать long press единственным доступом к редактированию.

Купленная карточка остаётся видимой на момент обратной связи. Перегруппировка выполняется мягко после взаимодействия, с сохранением позиции прокрутки, а не внезапно под пальцем. Цвет не единственный индикатор: галочка и слово «Куплено» обязательны. Снятие отметки доступно также через меню.

Если после покупки меняют количество/сам продукт, предложить вернуть позицию в «Нужно купить»; не оставлять новое требование незаметно купленным. Частичные покупки по долям количества — расширение после версии 1, если владелец подтвердит необходимость.

Дубликаты: предлагать объединение только при совпадении продукта, единицы и существенных уточнений. Не смешивать «молоко обычное» и «безлактозное». Никогда не суммировать несовместимые единицы молча. Пользователь может оставить две карточки.

## 8. Добавление текстом и библиотека продуктов

Вводить можно одну позицию или несколько строк. Обязательные случаи: переносы строк, запятые с учётом десятичных чисел, союз «и», русские формы количества. Перед созданием нескольких карточек показать редактируемый предпросмотр.

В библиотеке продукты нужны для быстрого выбора названия/изображения, не для продажи. Поиск локальный по словарю и синонимам плюс собственные семейные позиции. Нельзя показывать выдуманную доступность конкретного магазина.

Подготовить к первой визуальной приёмке минимум 24 готовых изображения: молоко, хлеб, сыр, яйца, масло, творог, йогурт, сметана, яблоки, бананы, помидоры, огурцы, картофель, морковь, зелень, лимон, курица, рыба, рис, макароны, чай, кофе, вода, бытовой товар. Для остального — качественная нейтральная карточка категории. Словарь может быть шире набора иллюстраций.

Создавать ассеты один раз и хранить локально/на собственном сервере. Не запускать платную генерацию при каждом добавлении. Не скачивать случайные картинки магазинов и не копировать упаковки известных брендов без основания. Для пользовательских фото — проверка типа/размера, удаление EXIF, разрешённое приватное хранение.

## 9. Голос: две независимые функции

### 9.1. «Надиктовать список»

Пользователь нажимает кнопку → даёт доступ к микрофону → видит явную запись и таймер → останавливает → аудио распознаётся → текст разбирается на товары → человек исправляет предпросмотр → подтверждает добавление.

Пример: «Молоко два пакета, хлеб один, сыр двести граммов и яйца десять штук» превращается в четыре редактируемые карточки. Распознавание не должно автоматически отправлять аудио семье. После сохранения списка временная запись удаляется согласно политике хранения.

Структура результата: исходный текст, массив предложений с названием/количеством/единицей/заметкой, диапазон исходного текста, признак необходимости уточнения. Не выдумывать confidence, если движок его не предоставляет; использовать честный `needsReview`.

Неуверенные слова сохранять, а не выбрасывать. Неизвестный продукт можно добавить вручную. Обычные фразы обрабатывать детерминированным парсером и словарём; сложные просьбы сохранять в заметке. Внешняя языковая модель не обязательна. Никогда не интерпретировать надиктованное как системные команды или инструкции серверу.

Browser SpeechRecognition имеет ограниченную совместимость и в части браузеров использует внешний сервер [S04]. Поэтому он не должен быть единственным обязательным способом. Основной совместимый путь: MediaRecorder → приватная загрузка → серверный SpeechToTextProvider → parser. Рабочий локальный вариант — faster-whisper с русским языком; модель и режим CPU/int8 выбирать после замера на реальном сервере [S11]. Скорость заранее не обещать. При нехватке ресурсов согласовать другой вариант, но не включать платный API молча.

### 9.2. «Голосовое сообщение»

Запись до 120 секунд, таймер, отмена, остановка, прослушивание перед отправкой, кнопка отправки. Получатель видит аватар, длительность, реальную аудиодорожку, play/pause, позицию и состояние доставки на сервер. Одна запись воспроизводится одновременно; запуск другой останавливает предыдущую. Автопроигрывание запрещено.

Сообщение относится к списку, при необходимости к конкретному товару. Возможен краткий текст до 1000 символов и реакция-сердце. Это не полноценный отдельный мессенджер с публичными контактами. Голосовые автоматически не превращаются в товары: для этого требуется отдельное подтверждённое действие.

### 9.3. Ошибки и совместимость записи

getUserMedia требует защищённого контекста и разрешения пользователя [S03]. Проверять поддержку MediaRecorder и MIME через isTypeSupported, не фиксировать единственный контейнер для всех браузеров [S05]. Рабочие кандидаты проверять в runtime; сервер приводит запись к совместимому формату и сохраняет оригинал только по необходимости.

При отказе микрофона — объяснение и ручной ввод. При прерывании звонком/блокировкой — сохранить доступный черновик и показать «Запись прервана»; не обещать запись в фоне. При закрытии экрана останавливать треки микрофона. Тишину не превращать в выдуманный текст. Состояния загрузки, обработки, ошибки и повторной отправки обязательны.

Офлайн можно записать локальный черновик, если браузер позволяет. Отправка и серверное распознавание выполняются после связи и открытия приложения; в интерфейсе это явно указано.

## 10. «Люблю! Целую.»

Точная надпись: **«Люблю! Целую.»**. Не заменять её на «Завершить заказ», «Оплатить» или «Оформить».

В черновике действие атомарно публикует готовый список и создаёт тёплое сообщение. В активном списке отправляет тёплое сообщение/обновление без дублирования всех позиций. Повторный случайный тап не создаёт вторую публикацию: pending-state и idempotency key обязательны.

Перед отправкой виден адресат: конкретный участник либо «Семье». Выбор адресата определяет получателя уведомления, а не приватность общего списка. Приватные списки между отдельными взрослыми вне семейного доступа — не часть версии 1.

Офлайн кнопка ставит операцию в очередь с текстом «Отправим, когда появится связь»; зелёное «Отправлено» показывать только после серверного подтверждения. После отправки список остаётся редактируемым. Сердце может коротко ожить; конфетти и навязчивые повторные анимации не нужны.

## 12. Бренд и визуальные принципы

Подробности в DESIGN_SYSTEM.md. Главный визуальный ориентир — последние утверждённые тёплые постеры с маленьким французским магазинчиком: сливочный, какао, шалфей, пыльная роза, бежевый. Это знак приложения о покупках, а не интерфейс реальной торговой точки.

Логотип один для всех. Сохранять форму магазина, полосатый навес, листовидные формы, рисунок букв и сердце. Не выбирать новое изображение из старой серии отдельно для каждого аккаунта. Подготовить горизонтальную/вертикальную версию, компактный знак, монохром и иконку. Исходные PNG-постеры не заменяют векторные мастер-файлы.

Крупные иллюстрации продуктов объёмные и узнаваемые, с натуральными материалами, без глаз и лиц. Стекло — умеренно прозрачные карточки с мягким краем и тенью. В приложении не использовать фотографию интерьера как шумный постоянный фон списка: интерьерные фото на постерах — настроение бренда.

Текст интерфейса настоящий HTML, а не текст, вырезанный с постера. UI-шрифт Inter, акцентный Nunito после проверки кириллицы и лицензии [S14–S15]. Название «Nunito Rounded» из генерации не считать точным именем установленного шрифта. Сам логотип не пересобирать случайным шрифтом.

## 13. Три темы и детский интерфейс

Мужская «Север»: сливочно-серый фон, глубокий сине-серый активный цвет, холодноватое прозрачное стекло, спокойные лаконичные детали.

Женская «Пудра»: сливочный фон, пудрово-бежевые и приглушённые розовые оттенки, мягкое стекло, какао для контрастного текста. Не ярко-розовый экран и не малиновая основная заливка.

Детская «Солнечная»: светлая сливочная основа, абрикосовый/сливочно-жёлтый и мятный, немного небесно-голубого; более простые подписи и крупные действия. Её должны отличать от мужской без чтения имени. Не копировать сине-зелёную мужскую палитру и не превращать интерфейс в кислотную игру.

Тема выбирается в профиле и сохраняется персонально. Взрослые имеют одинаковые функции и категории независимо от темы. Детские ограничения зависят от роли и разрешений; декоративная смена оформления не влияет на безопасность. Для детской роли можно упростить навигацию до списка/пожеланий, сообщений и семьи; настройки взрослых отсутствуют.

## 14. Обязательный динамический общий фон

**Событие запуска:** именно успешное локальное намерение отметить товар купленным в режиме покупки. Фон реагирует немедленно оптимистично, не ждёт распознавания цвета или загрузки картинки. Повторное подтверждение той же операции сервером не запускает эффект снова.

Меняется фон корневого экрана под всей сеткой, верхней панелью и нижней навигацией. Подсветка только самой карточки не выполняет требование. Логотип и фотографии товаров не перекрашиваются. Цвет текста и семантика ошибки/успеха стабильны.

Примеры: молоко — сливочный; хлеб — песочно-медовый; сыр — приглушённый золотистый; зелень — шалфейный; красное яблоко — тёплый приглушённый коралл; зелёное яблоко — мягкий зелёный; кофе — какао; ягодный йогурт — пудрово-ягодный. Цвет учитывает конкретный вариант изображения.

Для каждого продукта хранить заранее рассчитанный/подобранный `ambientColor`. Для загруженного фото извлечь цвет заранее: игнорировать прозрачность, белую подложку и глубокие тени. Если нет изображения, использовать цвет категории. Не рассчитывать цвет на каждом тапе через тяжёлую обработку на главном потоке.

Один переход 600 мс, допустимый диапазон 450–700 мс. Основа остаётся светлой: вклад цвета продукта ориентировочно 20–30%, а не сплошная яркая заливка. Предусмотреть максимум два фиксированных фоновых слоя с подготовленными радиальными градиентами и crossfade opacity. Нельзя накапливать слои на каждом тапе.

При нескольких быстрых отметках побеждает последнее действие; переход начинается из текущего видимого состояния без вспышки белого. Оттенок сохраняется до следующей покупки, отмены, выхода из списка или завершения похода. При отмене последней покупки — цвет предыдущей ещё купленной позиции текущего локального сеанса; при отсутствии такой позиции — базовый фон темы. Отмена старой карточки не меняет фон более новой купленной позиции.

При серверном отказе откатить и статус, и фон. При удалении/возврате последней выбранной позиции пересчитать визуальное состояние. История фоновых действий — локальная UI-история, а не глобальный статус семьи. По умолчанию удалённая покупка обновляет карточку, но не перекрашивает экран человека, который сейчас составляет список. Это выбранное правило поведения, его можно изменить по просьбе владельца.

В профиле: «Динамический фон» и «Уменьшить движение». При prefers-reduced-motion движение и перелив отключаются либо цвет меняется сразу; информация о покупке остаётся [S08]. Фон не должен непрерывно двигаться в простое. Проверить контраст на каждом товаре и каждой теме.

## 15. Уведомления и realtime

Разделить три вещи: realtime-обновление данных, внутреннее уведомление в приложении, системный Web Push. Push не является механизмом синхронизации и не доказывает, что человек прочитал список.

События для уведомлений: опубликован список, добавлен товар/группа, новый голос, участник идёт в магазин, пожелание ребёнка, товара нет. Каждую покупку синхронизировать, но не обязательно сопровождать отдельным push. По умолчанию прогресс покупок — внутри приложения, внешний push о каждой галочке выключен.

Отправитель не получает собственный push. Короткую серию добавлений объединять, например за 3 секунды: «Добавлено ещё 3 продукта». Уведомление имеет eventId, ссылку на список/товар и серверный статус прочтения. При открытии приложение запрашивает актуальные данные. Устаревший push об уже купленном товаре не возвращает его в нужные.

На iPhone Web Push доступен для приложений, добавленных на домашний экран, начиная с iOS/iPadOS 16.4; запрос разрешения должен следовать явному действию пользователя [S01]. Проверять возможности устройства, объяснять установку и не обещать уведомления обычной вкладке во всех случаях. Доставка зависит от сети, разрешений и настроек ОС; срок доставки не гарантировать.

Подписка хранится на устройство, допускается несколько устройств участника. 404/410 от push-сервиса инвалидирует подписку. Повторная отправка задач с backoff и дедупликацией. VAPID private key только на сервере. В preview системного уведомления по умолчанию не раскрывать голосовой текст и детские сведения: «В семейном списке есть обновление»; подробный preview включается настройкой.

Тихие часы и отключение звука — персональные. Веб-приложение не может гарантировать собственный звук системного push; пользовательский звук реализуется только при открытом приложении и допустимом браузерном взаимодействии. Не запускать аудиосообщения автоматически.

## 16. Офлайн и честные состояния доставки

После первого успешного открытия кэшируются оболочка и необходимые изображения. Активные разрешённые списки и исходящая очередь — IndexedDB с разделением по идентичности/семье. localStorage годится для малых визуальных настроек, но не является общесемейной базой.

Офлайн доступны уже загруженные списки, добавление, изменение и отметки с локальной очередью. Новые данные с другого устройства без сети не появляются — не имитировать их. При возвращении сети/фокуса/открытии приложения идёт реальная проверка сервера и отправка очереди. Background Sync используется только как дополнительная возможность; его поддержка ограничена [S06].

Операции зависимы по порядку: сначала публикация/создание списка, затем его позиции, затем связанные сообщения. Повторная загрузка аудио не создаёт копию сообщения. Ошибки показываются у конкретной операции. Конфликт не скрывается под общим «Всё сохранено».

Не хранить приватные API-ответы в общем service worker cache без привязки к сессии. На выходе очищать чувствительные данные, аудио, очередь и realtime-подключение этой идентичности. Если есть неотправленное — перед выходом предложить дождаться отправки либо удалить черновики. Не переотправлять очередь прежнего пользователя под новой сессией.

## 17. Архитектура реализации

Если готового приложения нет, рекомендуемая исходная архитектура: React + TypeScript strict + Vite для клиента; Node.js поддерживаемой LTS-ветки + Fastify для API; PostgreSQL; HTTP-команды и Socket.IO для realtime; worker для push/аудио/распознавания; файловое хранилище на собственном сервере с закрытым доступом. Это проектный выбор, а не единственный допустимый стек [S12–S13].

Для небольшого запуска достаточно модульного монолита API и worker с общей PostgreSQL; отдельный Python-процесс распознавания. Не вводить микросервисы и Redis без реальной потребности. Очередь заданий может работать через таблицу jobs с арендой задачи и повторами. Постоянный Node-процесс предпочтителен для выбранного realtime; не размещать его в среде, которая убивает соединение между запросами, без отдельного решения.

Статический frontend, API и realtime желательно за одним HTTPS-origin. Reverse proxy, сертификат, persistent volumes и резервные копии. Не предполагать уже существующий домен или доступы. Существующие сервисы владельца не заменять.

Версии библиотек проверяются и фиксируются на старте реализации, с lockfile и совместимой версией Node. Не писать `latest` в готовых production-инструкциях. Готовый проект должен запускаться по документированной команде, включая миграции; этот пакет ТЗ сам приложения не запускает.

Предлагаемая структура: `apps/web`, `apps/api`, `workers/speech`, `packages/contracts`, `packages/design`, `db/migrations`, `tests`, `docs`, `assets/brand`, `assets/products`. Разрешено упростить при сохранении границ и тестов.

## 19. Команды, события и защита от конфликтов

Каждая изменяющая команда содержит `operationId` UUID, цель, ожидаемую `version`, явное желаемое изменение. Покупка — `setStatus: purchased`, а не неидемпотентное `toggle` на сервере. Сервер получает пользователя из сессии, не из доверенного поля клиента.

Порядок: проверка сессии/членства/права → поиск operationId → блокировка строки списка/объекта → проверка версии → изменение и событие в одной транзакции → запись результата команды → commit → доставка realtime и push через outbox.

Счётчик `sequence` увеличивать транзакционно под блокировкой строки соответствующего списка. Не полагаться только на глобальный auto-increment как доказательство порядка commit. Клиент применяет последовательность без пропусков; при разрыве запрашивает недостающие события либо целый актуальный снимок. Блокировки PostgreSQL описаны в [S16].

Повтор одной operationId с тем же содержимым возвращает прежний результат без второго события. С другим содержимым — конфликт ключа. При двух одновременных одинаковых отметках «Куплено», когда состояние уже целевое, вернуть подтверждение без повторной покупки/уведомления. Противоречащий статус или правка той же версии — 409 с текущим объектом; не молча уничтожать свежую правку.

На клиенте 409 означает получить актуальное состояние, показать понятный выбор для несовместимых полей, затем отправить новую явную команду. Разные товары не должны блокировать друг друга логически. Нельзя заменять целый список старым массивом из клиента.

Socket.IO сам по себе не гарантирует получение каждого события после отключения; долговечный журнал, подтверждения и replay проектируются отдельно [S09]. При переподключении сначала snapshot/replay, затем применение ещё не подтверждённых локальных операций. Сервер проверяет доступ при подключении и подписке на список, а не только в интерфейсе.

## 21. PWA, совместимость и установка

Manifest: рабочие `id`, `name`, `short_name`, `start_url`, `scope`, `display: standalone`, иконки обычная/maskable и Apple touch icon. Под иконкой короткое «Купика», без длинного слогана. Не обещать, что установка меняет системную иконку в зависимости от темы аккаунта: в первой версии иконка единая.

Service worker версионирует статические ассеты и обновляет приложение безопасно: при неотправленных действиях не перезагружать страницу принудительно. Показать «Доступно обновление» и применять после сохранения. Проверить миграции IndexedDB между версиями.

Целевая проверка — актуальные на запуске iOS Safari и установленная PWA, Android Chrome и установленная PWA, desktop Safari/Chrome/Firefox. Дополнительно проверить минимально поддерживаемую iOS 16.4 при наличии реального устройства/стенда; если не проверено, не объявлять гарантированную поддержку. Использовать feature detection, а не только user-agent.

На iOS дать пошаговую установку через системное меню «Поделиться»; не обещать универсальный программный install prompt [S01]. При недоступном push приложение должно работать через обычную синхронизацию при открытии.

## 22. Доступность, движение и производительность

Обычный текст — контраст минимум 4,5:1, крупный — 3:1 [S07]. Проверять на худшем фоне каждого перелива. Минимальная зона интерактивного элемента по проектному стандарту 44×44 CSS px; для основных детских действий 48–56 px. Это наш целевой размер, не утверждение, что WCAG 2.2 AA всегда требует 44 px.

Поддержать экранные дикторы, фокус клавиатуры, Escape/закрытие панели, aria-live для важных изменений без чтения каждой анимации, масштабирование текста до 200%, понятный порядок фокуса. Карточка имеет доступное название, товар/количество/статус; не делать вложенные кнопки в кнопке.

Предусмотреть уменьшение движения и «Больше контраста/меньше прозрачности» как настройки. При отсутствии backdrop-filter поверхности остаются непрозрачными и красивыми. Анимации покупки не блокируют повторный ввод. Не делать постоянное покачивание всех карточек.

Цели для проверки на среднем мобильном устройстве: локальный отклик отметки до 100 мс; server-confirmed обновление второго открытого клиента p95 до 2 секунд при нормальной сети; отсутствие заметных долгих блокировок при серии тапов; стремиться к 60 fps. Это цели при заданном тестовом профиле, а не обещание для любой сети. Push в эти сроки не включать.

Оптимизировать первые изображения и JS, грузить остальное лениво, задавать размеры картинок, использовать WebP/AVIF с fallback. Реалистичный 3D-вид допустимо реализовать готовыми рендерами, без тяжёлого WebGL на каждой карточке. Не загружать целые бренд-постеры как фон приложения.

## 23. Безопасность и приватность

Обязательны проверки доступа на сервере для каждой операции, событий и медиа; защита от IDOR и повышения прав; CSRF при cookie-auth; ограниченный CORS; проверка Origin realtime; XSS-safe вывод текста; CSP по фактическим источникам.

Валидация размеров, MIME и фактического содержимого файлов; случайные storage keys; приватные файлы выдаются через проверяемый endpoint или короткоживущую подписанную ссылку после проверки доступа. Нельзя публичный `/uploads` с постоянными адресами голосов. Не загружать изображения по произвольному серверному URL пользователя без SSRF-защиты.

Токены, пароли, email, тексты голосов и аудио не отправлять в логи/внешнюю аналитику. Для наблюдения достаточно requestId, кода ошибки и длительности операции. Реальные детские записи не использовать как тестовые фикстуры и не публиковать в GitHub.

Распознавание локально на собственном сервере по умолчанию; перед передачей внешнему провайдеру показать условия и получить нужное согласование. Не писать «сквозное шифрование», если оно не реализовано. HTTPS и защищённое хранение не равны E2EE.

Сроки хранения объяснить пользователю. Удаление аккаунта/семьи отзывает сессии, подписки и доступы; для медиа — очередь удаления. Для резервных копий документировать отложенное исчезновение в пределах выбранного срока хранения. До публичного запуска проверить политику данных и требования к детским профилям для фактической аудитории; этот документ не является юридическим заключением.

## 24. Развёртывание и эксплуатация

Подготовить Docker/Compose либо столь же воспроизводимый способ запуска API, worker, PostgreSQL и распознавания. Приватное хранилище и база — persistent volumes. Секреты через environment/secret store, `.env` не коммитить. `.env.example` содержит только имена и безопасные заглушки.

Отдельные dev/test/prod окружения; тестовые аккаунты никогда не открывают реальную семью. Миграции выполняются контролируемо, перед потенциально несовместимыми изменениями — резервная копия. Зафиксировать порядок обновления frontend/API и возможность отката.

Health-check API и worker, журнал ошибок без персонального содержания, контроль очереди распознавания/отправки и свободного диска. Ежедневный backup базы и нужных медиа — предлагаемая настройка; срок 30 дней и реальную политику согласовать. Проверить восстановление хотя бы одного резервного набора в отдельное окружение.

В README готового приложения: требования к серверу, команды установки/миграций/старта, настройка HTTPS и Web Push, подключение STT, установка на iPhone/Android, проверка двух устройств, обновление, backup/restore, известные ограничения. Не использовать реальные секреты как примеры.

## 25. Этапы и результат каждого этапа

**M0 — визуальный прототип.** Подготовить мастер-логотип/иконки, компоненты трёх тем, карточки и основные экраны. Реализовать локальный сценарий добавления, отметки с общим фоном, отмены, темы и запись с предпросмотром. Показать скриншоты одной и той же сетки продуктов в трёх темах. Имитация семьи маркируется как демо. Длительные серверные работы можно вести параллельно, но не выдавать макет за приложение.

**M1 — настоящий основной сценарий.** Авторизация, семья, два взрослых, PostgreSQL, общий список, добавление/правки/покупки, realtime, конфликтные операции, офлайн-очередь, восстановление связи и история. Проверить двумя независимыми сессиями, затем двумя устройствами.

**M2 — голос, дети, уведомления.** Полноценные аудиосообщения, распознавание русского списка с предпросмотром, разрешения детей, приглашения/отзыв, PWA, Web Push и ограничения iOS. Провести проверки браузеров.

**M3 — доводка и запуск.** Реальные изображения, визуальная приёмка, доступность, безопасность, нагрузочный профиль, резервное восстановление, инструкция эксплуатации. Настройка домена/публичный запуск только после согласия владельца.

После этапа: коммит, перечень готового, результаты выполненных тестов, скриншоты, список непроверенного и конкретные блокеры. Продолжать по плану, не требуя подтверждения каждого мелкого CSS-изменения; отдельное согласие нужно для нового бюджета, публичного развёртывания и существенного изменения концепции.

## 26. Definition of Done

Готовность первой версии определяется всем чек-листом ACCEPTANCE.md, а не только внешним видом. Обязательны: два независимых клиента; работающий backend; синхронизация после разрыва; корректные права детей; реальные голосовые; распознавание с исправлением; PWA/уведомления на поддерживаемых устройствах; три темы; единый логотип; отсутствие цен; общий динамический фон; тесты и воспроизводимая установка.

Если нет доступа к устройству, серверу или финальному ассету, указать это как непроверенный пункт с планом проверки. Не заменять обязательную функцию вечной заглушкой «скоро». Запуск без одной из обязательных функций допустим только как явно обозначенная промежуточная версия по согласованию владельца.
