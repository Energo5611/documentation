# Голосовой ассистент и автоматический подбор 3D-товара

**Дополнение версии 1.2 • 10.10.2026.** Новое обязательное требование владельца: голосовой ассистент должен не только распознать/выбрать нужный товар, но и подобрать подходящую 3D-модель для его карточки. Читать вместе с TECHNICAL_SPEC.md, PHONE_AND_FAMILIES.md и DESIGN_SYSTEM.md. Это уточнение разделов 7–10, 14, 18 и этапов M0–M3 базового ТЗ; остальные требования сохраняются.

## 1. Что получает пользователь

Человек говорит обычной фразой, а не диктует команды по специальному шаблону. Пример: «Добавь два пакета молока по литру, батон и килограмм зелёных яблок». Ассистент готовит три карточки: молоко с количеством упаковок и объёмом каждой, именно батон, именно зелёные яблоки. У каждой автоматически подобран подходящий объёмный объект.

Количество/название/уточнение видны текстом, картинка помогает узнать товар. Подбор изображения не определяет марку, наличие в магазине, состав, размер упаковки или цену. Цена вообще не входит в модель приложения.

Результат сначала показывается в предпросмотре. Пользователь может поправить текст, количество, упаковку или картинку и затем подтвердить добавление. Для детского профиля подтверждение создаёт пожелание, а не обходит разрешение взрослого.

## 2. Три разных понятия

**Распознавание речи** получает текст из аудио. **Понимание просьбы** выделяет товар, количество, единицы, признаки и неоднозначности. **Подбор визуального ассета** выбирает уже существующую разрешённую модель/вариант и её превью. Один движок распознавания сам по себе не выполняет все три задачи.

**Настоящая 3D-модель** — геометрия и материалы, например GLB/glTF. **3D-рендер** — обычное плоское изображение объёмного объекта, WebP/PNG. Называть PNG «готовой редактируемой 3D-моделью» нельзя. glTF предназначен для передачи и загрузки 3D-ассетов [V01].

Предлагаемая архитектура: у основных продуктов подготовить настоящие мастер-модели и лёгкие рендеры из них. В сетке карточек показывать рендер, чтобы не запускать десятки отдельных 3D-сцен; GLB загружать только при явном открытии 3D-просмотра в деталях. Постер/отложенная загрузка поддерживаются, например, model-viewer [V02]. Сама кнопка покупки остаётся покупкой, а не поворотом модели.

Интерактивное вращение в деталях — предлагаемая возможность, не новый обязательный режим для каждого экрана. Обязательны автоматический подбор подходящего ассета и корректный объёмный вид. Для первых базовых товаров в deliverables должны быть реальные модели/исходники; временные render-only ассеты отмечать именно так и отдельно согласовать исключения.

## 3. Конвейер

`Аудио → текст → структурированная просьба → точный тип товара → разрешённый визуальный вариант → предпросмотр → подтверждение → общая карточка`.

1. Сервер проверяет сессию, принадлежность текущей семье/списку и права на добавление. Загруженное аудио приватное.
2. SpeechToTextProvider возвращает текст. Базовый кандидат — локальный faster-whisper из основного ТЗ [S11]. Формат записи выбирается runtime; browser SpeechRecognition не единственная зависимость из-за ограничений поддержки [S03–S05].
3. ProductIntentParser выделяет массив намерений: исходный фрагмент, канонический тип или unknown, количество/единицу, объём одной упаковки, явно указанные признаки, отрицания и вопросы.
4. ProductResolver сопоставляет семантический тип с каталогом и, при разрешении, сохранённым семейным словарём. Не использует историю чужих семей.
5. ProductVisualResolver выбирает approved-ассет нужного типа/варианта. Он возвращает ID/версию, тип соответствия, варианты для исправления и объяснение, а не произвольный внешний URL.
6. Предпросмотр показывает карточки и только существенные уточнения. Не заставлять вручную выбирать изображение каждого обычного продукта: уверенный подходящий вариант выбирается автоматически.
7. Подтверждение публикует карточки атомарно и идемпотентно. Выбор ассета и его версия записываются на сервере, чтобы оба участника видели одинаковый продукт.

Одинаковый ProductResolver используется для ручного ввода и надиктовки. Нельзя получать красное яблоко при текстовом запросе и зелёное при том же голосовом запросе без причины.

## 4. Понимание количества и признаков

«Два пакета по литру» = quantity 2, unit уп., packageSize 1 л. Это не две независимые просьбы и не один пакет объёмом 2 л. «Молоко 3,2%» сохраняет жирность отдельно. «Сыр двести граммов» — масса покупки, не автоматический выбор двухсотграммовой фирменной упаковки.

«Батон» — отдельный тип хлеба, не синоним любого хлеба и не французский багет. «Молочка» — неопределённая категория, не всегда молоко. «Паста» без контекста может быть неоднозначной. «Масло» при отсутствии уточнения/явного семейного выбора требует вопроса «Сливочное или растительное?». Старые широкие синонимы в примерах не использовать как безусловные соответствия.

«Зелёные, не красные яблоки» должно исключить красный вариант. «Молока два… нет, три пакета» — исправление количества в текущем предпросмотре, не две карточки. «Хлеб не нужен» в процессе надиктовки исключает кандидат из текущей просьбы; НЕ удаляет уже общий товар без отдельного подтверждения.

Неявные размер, бренд, вес и количество не выдумывать. Если «пакет молока» не уточняет тип упаковки, общий нейтральный рендер может обозначать молоко, но не записывать из его формы выдуманную bottle/carton-характеристику в данные. Явное «в бутылке» имеет приоритет при подборе изображения.

Признаки вроде «безлактозное» и «без сахара» сохраняются как требование пользователя и показываются текстом. Нейтральная иллюстрация не доказывает состав реального продукта; ассистент не должен давать такую гарантию. Не снимать эти ограничения ради красивой подходящей картинки.

## 5. Как выбирать модель

Сначала жёсткие ограничения, потом ранжирование. Не использовать один общий балл сходства, который позволяет яблоку заменить грушу из-за похожего цвета.

Жёсткие фильтры: approved и реально доступный ассет; разрешённая лицензия/область доступа; совпадающий тип товара; отсутствие противоречия явно указанным визуальным признакам. Если точного типа нет, fallback разрешён отдельно и явно помечается, а не проходит как exact.

После фильтров приоритет: точный подтверждённый выбор пользователя в текущем черновике → сохранённый для этой семьи выбор, не противоречащий новой фразе → тип и явно заданные форма/упаковка/цвет → нейтральный вариант того же типа → изображение категории → общий стильный placeholder.

Результат `matchLevel`: `exact_visual`, `generic_product`, `category_fallback`, `placeholder`. Это степень соответствия иллюстрации, НЕ гарантия марки/состава/наличия товара. `selectionReason` хранит понятное основание. Если есть внутренний score, не показывать его как «вероятность правильности 99%» без калибровки.

Для зелёного яблока выбирается зелёный вариант модели яблока. Цвет модели не меняется на розовый в женской теме и не становится синим в мужской. Темы меняют поверхности интерфейса, не смысл продукта.

Если подходящих вариантов несколько, по умолчанию один наиболее нейтральный; «Изменить изображение» открывает 3–6 допустимых вариантов. Если неоднозначность касается САМОГО товара, короткий вопрос с вариантами, а не тихий случайный выбор.

## 6. Короткий уточняющий диалог

Пример: пользователь «Добавь масло» → ассистент «Сливочное или растительное?» → «Сливочное, одну пачку» → карточка масла и подходящая модель бруска/пачки. Другой пример: «Добавь яблоки» → нейтральное яблоко без выдуманного сорта; после «лучше зелёные» тот же draftItemId получает зелёный вариант, количество не сбрасывается.

Уточнение можно дать текстом, голосом или кнопкой. Контекст ограничен текущим приватным предпросмотром; он не включает всю историю семей и не прослушивает комнату. Каждая следующая запись запускается явным действием. Тайм-аут контекста не должен приводить к применению ответа к старому списку.

Текст ответа обязателен. Короткое озвучивание вопроса/подтверждения — предлагаемая персональная настройка. При использовании browser speechSynthesis доступны голоса текущего устройства, нельзя гарантировать единый голос на всех телефонах [V03]. Запись микрофона останавливать до воспроизведения ответа, чтобы ассистент не распознал себя. Нет озвучивания без действия пользователя или поверх чужого аудиосообщения.

Вместо бесконечного диалога после 1–2 неудачных уточнений предложить ручное исправление; лимит — проектная настройка. Остальные понятные карточки не теряются. Пользователь может оставить неизвестный товар с оригинальным названием и нейтральной иллюстрацией.

## 7. Реестр ассетов

Отдельные сущности `ProductDefinition` (смысл товара) и `ProductVisualAsset` (как он выглядит). Одна модель может иметь несколько проверенных вариантов материалов; несколько упаковок соответствуют одному смысловому продукту. Не связывать все бизнес-данные с именем файла.

Поля визуального ассета: id, semanticType, visualVariant, tags, explicitAttributes, scope public/family, familyId nullable, status draft/approved/retired, kind model3d/render_only/placeholder, version, sourceAsset, modelStorageKey nullable, posterStorageKey, shadowStorageKey nullable, licenseId, attribution, checksum, bounds/anchor/cameraPreset, ambientColor, fallbackAssetId.

URL выдаются только из реестра/защищённого хранилища. Ассистент не придумывает путь `/models/milk.glb`, если такого файла нет. В seed-реестре статус planned и null-пути означают ПЛАН, не готовый ассет; runtime resolver такие записи не выбирает как доступные модели.

Для основных продуктов подготовить настоящий GLB и WebP/PNG-превью с прозрачностью. Без внешних сетевых ссылок в текстурах; проверить размер/количество текстур, меши, материалы, лицензию и отсутствие лишних метаданных. Предлагаемые бюджеты после оптимизации: рендер до 200 KiB на карточку, GLB до 2 MiB для простого предмета, текстуры до 1024 px по стороне. Это стартовые цели, исключения обосновывать замерами, а не обещания всех моделей.

Рендерить одинаково: мягкий студийный свет сверху слева, схожий ракурс 3/4, масштаб внутри общей зоны, натуральные материалы. Отделённая тень объекта помогает парению. Не перекрашивать продукт ради палитры; стилизация достигается светом, поверхностью и окружением.

Для загрузки/оптимизации моделей выбранный renderer и расширения проверить совместно. model-viewer поддерживает GLB/glTF, постеры и отложенную загрузку; некоторые декодеры по умолчанию берутся с внешнего CDN — при собственном размещении и CSP это настроить явно [V02]. Не подключать WebGL на каждой карточке в сетке, не авто-вращать все продукты.

## 8. Минимальная библиотека и её пополнение

У первого работающего релиза должны быть не только JSON-ID, но проверенные реальные базовые ассеты. Минимум 24 базовых товара из ТЗ плюс необходимые варианты для приёмочных фраз: молоко в бутылке/пакете/нейтральной упаковке; батон отдельно от багета и формового хлеба; красное/зелёное яблоко; сливочное масло отдельно от растительного. Возможен общий мастер с материалами/формами, но варианты визуально проверяются.

Следующий ориентир расширения — 80–120 частых продуктов; это предложение, не обязательство создать их в ходе подготовки документации. Единая публичная библиотека может обслуживать разные семьи, потому что содержит нейтральные фирменные ассеты, а не пользовательские данные.

Новую модель не генерировать при каждом диктовании. При отсутствии — безопасный fallback сейчас; заявка на пополнение в очередь контента без текста личного аудио. Создание/покупка/генерация модели — отдельный контролируемый этап: источник → проверка прав → унификация стиля → оптимизация → рендер → QA → публикация версии. Реальные расходы только с согласия владельца.

Если используется генерация изображения, результат маркируется render_only, не glb. Если используется генерация 3D, проверить полученную геометрию и материалы, а не только рекламный preview. Автоматически скачивать случайный результат интернет-поиска и отдавать всем семьям запрещено. Факт бесплатности просмотра модели не подтверждает право использовать её в публичном приложении; лицензию фиксировать для каждого ассета.

## 9. Выбор, который запоминает семья

После ручного исправления можно предложить «Использовать этот вариант в нашей семье». Согласованный `FamilyProductPreference` хранит familyId, нормализованный запрос/semanticType, assetId/variant, ограничения и updatedAt. Новая явная просьба всегда выше старого предпочтения.

«Наше обычное молоко» можно связать с ранее явно выбранным вариантом этой семьи. Если записи нет или их несколько, задать вопрос. Не выдумывать такую историю. Переход в другую семью не переносит её предпочтение автоматически. Нельзя использовать голос/детские пожелания одной семьи для обучения общего каталога без отдельного основания и согласия.

## 10. Связь с общим цветовым фоном

В выбранном варианте хранится `ambientColor`, подготовленный вместе с рендером. Для зелёного яблока он зелёный, для красного — приглушённый коралловый. Не получать доминирующий белый от фона PNG и не определять цвет заново на каждом тапе.

При подтверждении карточки сохраняются assetId, variantId, assetVersion и snapshot базового цвета. На всех устройствах выбирается тот же визуальный вариант; различается только смесь с персональной темой. При покупке общий фон реагирует по разделу 14 основного ТЗ. Изменение ассета в предпросмотре не отмечает товар купленным и не посылает семье отдельное уведомление.

Замена модели при редактировании существующей карточки — версионированная операция. Изображение уже купленного товара не должно незаметно менять смысл покупки. При недоступном файле показывать локальный fallback, сохраняя название/количество/исходный выбор, а не менять продукт.

## 11. Контракт и серверные операции

`AssistantDraft`: id, familyId, listId, creatorId, revision, source transcript/manual, originalText, items[], clarificationQuestions[], expiresAt. У item: draftItemId, sourceText, semanticType nullable, displayName, quantity decimal nullable, unit nullable, packageSize nullable, attributes, exclusions, note, needsReview, visualSelection.

`visualSelection`: assetId nullable, variantId nullable, assetVersion nullable, kind, matchLevel, selectionReason, ambientColor, alternatives[] и state available/placeholder/missing. Источники/лицензии относятся к asset registry, а не произвольному ответу NLU.

Операции: POST `/assistant/drafts` из текста/готовой транскрипции; GET `/assistant/drafts/:id`; PATCH `/assistant/drafts/:id` для исправления; POST `/assistant/drafts/:id/replies`; POST `/assistant/drafts/:id/confirm`; GET `/product-visuals/search` в разрешённой области; POST/PATCH `/families/:id/product-preferences` после явного согласия. Не создавать второй несвязанный STT: существующий speech job отдаёт результат в этот же draft.

Каждая операция проверяет семью/автора/список/роль. Конфликт revision не теряет исправления. После confirm повтор той же operationId не дублирует карточки. Если пользователь закрыл draft/перешёл в другой список, поздний ответ worker не публикует товары сам. Удаление и действия purchased по голосу вне этого сценария не выполняются без отдельного разрешённого подтверждения.

## 12. Реализация без фиктивного ИИ

Базовая схема локальная: STT → валидируемый парсер/словарь → поиск семантического типа → детерминированный resolver по тегам. Для свободных сложных фраз допускается NLU-адаптер локальной языковой модели после оценки сервера либо внешний согласованный провайдер. STT и NLU — разные интерфейсы, не обещать, что одна библиотека распознавания понимает все товары и выбирает 3D сама.

Даже при использовании языковой модели её ответ только структурированные кандидаты, проверенные схемой. Модель не получает секреты, доступ к чужим семьям, произвольную сеть или SQL. Допустимые assetId выдаёт реестр. Для неоднозначных запросов предпочтительнее уточнение, чем уверенная ошибка. Простые запросы не обязаны платить за внешний LLM.

Ограничения CPU, длительности, очередей и расходов per family. Семейные данные не попадают в общие логи. При недоступном STT остаётся текст; при недоступном NLU — простые правила и исправление; при недоступном registry — уже кэшированный разрешённый fallback. Приложение не зависает на «Подбираю модель» бесконечно.

## 13. Что проверить

Все пункты ниже исходно NOT RUN; конкретные фразы в `data/assistant-visual-cases.json`.

- [ ] V01. Одна фраза с несколькими товарами автоматически даёт несколько осмысленных карточек с выбранными подходящими визуальными ассетами.
- [ ] V02. Батон не багет; яблоко не груша; зелёное яблоко не красное. Визуальные ограничения важнее мягкого score.

## 14. Дополнение к этапам

M0 — показать автоматический визуальный подбор на локальном тестовом каталоге и отдельную панель исправления; демонстрация помечена как демо. Параллельно подготовить первые реальные 3D-ассеты.

M1 — серверный реестр, versioned visual selection в ListItem и синхронизация двух устройств. Изоляция family preferences.

M2 — полный голосовой конвейер, уточнения и предпросмотр с реальными моделями, те же функции для текста. Пройти assistant-visual-cases.json и реальные записи.

M3 — проверенные лицензии, оптимизация/кэширование, отсутствие сетевых утечек, бюджет STT/NLU, доступность, fallback и реальные устройства. Предоставить перечень готовых моделей, отдельно список render-only исключений и отсутствующих ассетов. Не считать заполненный JSON-реестр готовой библиотекой.

## Технические первоисточники дополнения

V01 — [Khronos glTF](https://www.khronos.org/gltf/): формат передачи/загрузки 3D. Не утверждаем, что любая GLB автоматически оптимальна для любого телефона.

V02 — [model-viewer: loading](https://modelviewer.dev/examples/loading/): GLB/glTF, poster, lazy loading, декодеры и изменение нагрузки. Это возможный renderer, не обязательная зависимость.

V03 — [MDN: SpeechSynthesis.getVoices](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis/getVoices): голоса текущего устройства.

Остальные обозначения S03–S05 и S11 — в SOURCES.md. Источники проверены 10.10.2026; версии библиотек и поддержку устройств перепроверить перед реализацией. Правила подбора, схема данных, бюджеты и этапы — проектные решения.
